# Architecture

## Current implementation (execution slice)

The Python CLI and JSON ledger accept and list tasks, atomically claim an exact task ID, and validate state transitions. `factory task-run-next` atomically claims the oldest queued low/medium-risk task by creation timestamp; manual and automatic claims share one atomic execution slot. The supervised user systemd timer waits five minutes after activation before its first run, then schedules 30 minutes after the oneshot service becomes inactive (`AccuracySec=1min` permits coalescing), one task per run. Stale automatic recovery checks Linux PID plus `/proc` start-time identity before applying age thresholds (15 minutes for preflight claims; two hours for execution-stage claims); a manual claim blocks dispatch and is never automatically recovered. The service wrapper checks the pinned `FACTORY_RUNNER_SHA`, clean checkout, and expected Git origin on every invocation. The service cgroup prevents the timer from overlapping lingering descendants; direct CLI invocations do not have that service-level guarantee. The executor uses a bounded Codex CLI worker, a disposable Git worktree, a separate Docker pytest verifier, and a GitHub draft-PR publisher. High-risk tasks remain unselected by the automatic queue. The coordinator rejects dirty source checkouts, protected policy/CI/ownership/verifier/deployment changes, symlinks, malformed diffs, and heuristic credential-pattern matches. It refreshes `origin/<base>`, verifies the configured GitHub remote, checks write permission and server-enforced human review, then creates and reads back an exact-commit draft PR.

The worker is launched with Codex CLI's generated `factory-worker` permission profile, a dedicated `CODEX_HOME`, a per-run `HOME`, a minimal environment, and a fresh empty `GH_CONFIG_DIR`. The profile denies filesystem access outside the task workspace except read-only repository Git metadata, disables sandbox networking and web search, and marks the task workspace untrusted so project-local Codex config and hooks are skipped. Captured subprocess output is capped at two million characters per stream (up to four million combined); exceeding either cap immediately kills the command's process group. Stdin writes run concurrently under the same command deadline, so a child that never reads input cannot stall timeout handling. The isolated verifier is a distinct container with `--network=none`, a read-only checkout, dropped capabilities, no-new-privileges, resource limits, and writable temporary storage. It runs the submitted tests, which may be worker-authored; it does not independently establish their correctness. Coordinator-owned Git commits and publication happen only after verification.

The public repository does not yet have active CI checks. The baseline executor has completed a docs-only draft PR; the new timer-driven automatic dispatcher has not been exercised end-to-end. Local host/Docker suites and focused Codex sandbox probes have passed, but live authenticated task execution and GitHub publication remain unverified. The profile is a host-side Codex/bubblewrap/seccomp layer—not a separate VM or a proof against sandbox/runtime/kernel escape; `/proc/1/environ` was readable in a probe, so the worker environment is kept minimal.

## Flow

```text
Overseer (Danny) decomposes an owner-authorized goal → metadata queue → automatic low/medium-risk selection → deterministic preflight/policy → exact-ID claim
   → disposable Git worktree → Codex CLI `factory-worker` permission profile
   → protected-control checks, symlink, whitespace, and heuristic secret checks
   → network-disabled Docker pytest verifier → coordinator-owned commit
   → exact-SHA draft PR → human review/merge/deploy
```

## Components and boundaries

- **Task ledger:** canonical task IDs, immutable intent, acceptance criteria, risk tier, revision, status, timestamps. The repository and durable task backend—not model conversation history—own status. A task's `claimed_by` field is an operator-supplied label; an automatic claimant identity records Linux PID plus `/proc` start-time ticks and is used only as a conservative liveness signal, never as authentication or authorization.
- **Coordinator:** preflights worker, verifier, GitHub permissions, branch protection, source cleanliness, remote identity, and base ref. Both `task-run` and automatic `task-run-next` atomically claim before preflight and requeue on a preflight exception; all active claims share one lock-protected execution slot. Automatic selection runs one low/medium-risk task per invocation; high-risk tasks remain queued. Any manual active claim blocks automatic dispatch, and manual claims block when any task is already active. A live or unidentifiable automatic claim blocks later automatic runs. Stale recovery checks PID plus `/proc` start-time identity, then applies age thresholds: preflight claims are requeued after 15 minutes; execution-stage claims are blocked after two hours for inspection before retry. Legacy claims without start-time identity fail closed. Wall-clock adjustments can delay or accelerate age classification; execution-stage claims are never automatically retried. The user systemd timer starts five minutes after activation, then schedules 30 minutes after the oneshot service becomes inactive; disable it to prevent future starts, and stop the service separately to abort an active run. The service cgroup supervises descendants; the wrapper sends `SIGTERM`, waits, then `SIGKILL` to remaining live process-group members on timeout; direct CLI invocations do not receive the cgroup guarantee. Preflight failures retry the same oldest task and can pause later queued work until resolved. Automatic process identity checks are a liveness guard, not a durable lease; there is no automated cost accounting or required CI check.
- **Worker adapter:** Codex CLI only for now. Each task gets a disposable worktree, a dedicated Codex home, and a generated per-run permission profile. The sandboxed command receives no GitHub tokens or inherited host API-token variables; only read-only access to common repository Git metadata is added so Git status can work. The profile denies access to the authentication home and network, but the outer Codex CLI still needs that authentication; focused local probes are not a proof against sandbox/runtime/kernel escape or same-UID attacks.
- **Verification:** pytest runs in a fixed local Docker image with no network and a read-only checkout. Tests may be added or changed by the worker, so the green result is not independent of the proposed test diff and does not prove test correctness; human review is mandatory. Protected paths are `.github/**`, root and `docs/CODEOWNERS`, `.gitattributes`, `.gitmodules`, `docs/CHARTER.md`, `docs/THREAT_MODEL.md`, `docker/**`, `deploy/**`, `scripts/**`, and `pyproject.toml`; remote branch protection is enforced by GitHub. The result is bound to the base and exact commit SHA in the manifest and draft-PR readback.
- **Publication:** the publisher requires GitHub write access and at least one enforced human approval (including admins) on the base branch. It pushes only a verified task branch and creates a draft PR. It cannot merge or deploy.
- **Decision model (optional Jev):** closed-set routing/risk/evidence classification only. First run shadow-only; no permission, merge, deployment, or policy-waiver authority.
- **Observability:** secret-free run manifests bind task ID, attempt ID, branch, base SHA, commit SHA, draft-PR URL, verification summary, and completion time. Manifests use restrictive local file permissions.

## Authority model

Policy is enforced outside the model loop. Workers may propose source, test, and factory-code changes in disposable worktrees, but cannot modify the task ledger, `.github/**`, root/docs CODEOWNERS, charter, threat model, verifier image/configuration, deployment/timer files, scripts, or `pyproject.toml`. The running coordinator remains outside the worker worktree; proposed changes do not take effect until human review and merge. GitHub credentials remain in the post-verification publisher process, not the worker. The sandboxed command cannot read the dedicated Codex auth path under the tested profile, but the outer Codex CLI retains access; keep the auth sensitive and treat the profile as a mitigation, not an absolute boundary. State/work directories are private; the single-user service does not protect against a malicious same-UID process. Every privileged operation has its own authorization boundary.

## Why not install a large orchestrator immediately?

The source review suggests the queue, policy, evidence, and review boundary matter more than adding agent count. Avoid duplicated task state, retry logic, and competing control planes. Add durable coordination or multiple workers only after measured requirements justify them.
