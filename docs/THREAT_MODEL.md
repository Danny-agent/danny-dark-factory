# Threat model

## Assets

Source code, GitHub write access, Codex account material, build/test integrity, task evidence, secrets, production systems, and reviewer attention.

## Threats

- Prompt injection in task descriptions, issues, repository files, comments, dependencies, or tool output.
- Worker modifies tests, policy, CI, or its own constraints to create false-green verification.
- Duplicate/stale worker claims, retries, lost state, stale base refs, or incorrect completion.
- Secret disclosure through environment variables, Codex auth files, workspace contents, logs, artifacts, or network access.
- Malicious or compromised dependency/agent/runtime; unsafe shell, symlink escapes, or destructive operations.
- Review overload, rubber-stamping, or output metrics hiding escaped defects.
- A Docker/kernel or Codex sandbox escape affecting the shared host.

## Current controls

- The queue validates metadata and state transitions. Exact task IDs are atomically claimed; queued low/medium-risk tasks enter the automatic dispatcher, while high-risk tasks remain unselected. Manual and automatic claims share one serialized execution slot. The automatic claimant identity is Linux PID plus `/proc` start-time ticks, used only as a conservative liveness signal; claimant strings are not authentication or authorization.
- The worker prompt treats task JSON as untrusted. A disposable Git worktree is passed to Codex CLI with a generated `factory-worker` permission profile: root-deny filesystem policy, task-workspace writes, read-only worktree/common Git metadata, `.codex` and `.agents` read-only, network and web search disabled, a per-run `HOME`, and an allowlisted child environment. The outer Codex CLI uses a dedicated `CODEX_HOME` for authentication; the sandboxed command is not given that directory. Runtime rejects Codex base-config keys outside the `projects.<absolute-path>.trust_level` allowlist and marks each task workspace untrusted so project-local config/hooks are skipped. The worker gets a fresh empty `GH_CONFIG_DIR`; GitHub tokens and inherited host API-token variables are not passed to it.
- The coordinator rejects dirty source checkouts, mismatched GitHub origins, unavailable base refs, protected policy/CI/ownership/verifier/deployment path changes, worktree Git-pointer changes, worker-created symlinks, whitespace failures, submodule/LFS changes, and common credential patterns in staged Git blobs (maximum 64 MiB total). Protected repository paths are `.github/**`, root and `docs/CODEOWNERS`, `.gitattributes`, `.gitmodules`, `docs/CHARTER.md`, `docs/THREAT_MODEL.md`, `docker/**`, `deploy/**`, `scripts/**`, and `pyproject.toml`; GitHub branch-protection settings are enforced remotely. The timer wrapper also checks the exact local runner SHA pin, clean checkout, and expected `origin` on every invocation. State/work directories are runner-owned mode `0700` beneath a private data root, and path ancestors must not be writable by another user. Same-UID malicious processes are outside this single-user service's security boundary. Source and test changes may be proposed but are not trusted until human review. Credential scanning is heuristic and cannot guarantee that a diff is secret-free.
- The isolated verifier uses a pinned Python base image, local image only (`--pull=never`), no network, read-only source mount, dropped capabilities, no-new-privileges, PID/CPU/memory limits, and a temporary filesystem. It executes the proposal's tests; worker-authored tests are not independent of the proposal and do not establish test correctness. Coordinator subprocess stdout and stderr each have a separate two-million-character capture cap (four million combined); exceeding either cap immediately kills the process group. Stdin is delivered concurrently under the same timeout, so blocked input cannot bypass the deadline.
- For automatic dispatch, the ledger atomically claims the oldest eligible task before preflight; a preflight exception releases it to `queued`. `task-run` also claims before preflight. Every active manual or automatic claim blocks other claims under the same ledger lock; manual claims are never automatically recovered, so an abandoned manual claim requires operator inspection. A live or unidentifiable automatic owner blocks later dispatches. Recovery uses PID plus `/proc` start-time identity to detect PID reuse, then applies its age threshold: preflight claims are requeued after 15 minutes; `planning`, `implementing`, or `verifying` claims are blocked after two hours so uncertain side effects are inspected. Age is measured from the latest wall-clock `updated_at` transition; backward clock changes delay recovery, while large forward changes may classify a dead-owner claim early. Execution-stage claims are never automatically retried. Legacy claims without start-time identity fail closed and require manual inspection.
- Coordinator-owned commits occur after verification. The publisher pushes only a verified branch and creates a draft PR, checks the exact base/head SHA readback, and never merges or deploys.
- Manifests are local, secret-free by design, and written with restrictive file permissions.
- `main` is protected: PR required, one code-owner approval, stale approvals dismissed, last-push approval and conversation resolution required, admin enforcement, and force-push/branch deletion blocked. No required CI checks are configured. `pc099`'s write invitation is still pending acceptance; the account's active permission remains read until accepted.
- The workflow file remains a checked-in template; the authorized GitHub CLI grant still needs the `workflow` scope before installation.

## Automatic timer

- The included user-level timer (not enabled merely by a repository checkout) waits five minutes after activation before its first run, then schedules 30 minutes after the oneshot service enters the inactive state; `AccuracySec=1min` permits coalescing. It processes the oldest queued low/medium-risk item, one task per invocation, with no per-task confirmation prompt; high-risk tasks stay queued. Disabling the timer prevents future starts. The later invocation reports `busy` for any active manual or automatic claim and does not start another task. Automatic recovery applies thresholds from the latest wall-clock `updated_at` transition only after PID plus `/proc` start-time identity is confirmed absent; a backwards clock delays recovery and a forward jump can accelerate classification of a dead-owner claim. Dead-owner preflight claims are requeued after 15 minutes; execution-stage claims are blocked after two hours for manifest/GitHub inspection. Manual claims are not auto-recovered and require operator inspection if abandoned. Legacy claims without start-time identity require manual inspection. On dispatcher timeout, the wrapper sends `SIGTERM` to its process group, waits three seconds, sends `SIGKILL` to remaining live members, then waits up to three more seconds; zombie members are treated as non-executing, while unkillable live processes are reported. The user service uses `ExitType=cgroup` and `KillMode=control-group` so lingering descendants keep it active and are terminated on timeout/stop. Use this supervised service for unattended execution; direct CLI invocations do not gain that cgroup guarantee. The timer wrapper checks the pinned runner revision, clean checkout, and origin on each invocation. Timer setup stores paths only, never credentials.

## Explicit non-claims

- Independent-verification caveat: the verifier runs tests from the proposed worktree; because workers may change tests, the result is not independent of those test edits. Human code-owner review is mandatory.

- Focused local probes against Codex CLI's Linux bubblewrap/seccomp sandbox blocked direct reads of the dedicated auth file and `/proc/1/root` traversal, writes to Git metadata, Docker/systemd sockets, and network-interface inspection while allowing task-workspace writes and read-only Git status. `/proc/1/environ` was readable inside the sandbox, so the child environment must remain allowlisted; process memory reads were denied in the probe. These are targeted checks, not adversarial escape testing. The outer Codex CLI necessarily uses the dedicated auth store; do not assume the profile is a hardened boundary against Codex, bubblewrap, seccomp, kernel, or same-UID attacks.
- Docker shares the host kernel. The container is a useful test-isolation boundary, not a proof against kernel/runtime escapes or hostile code in a multi-tenant production setting.
- Passing tests, heuristic secret scanning, and a draft PR are not proof of correctness or safety. Human review is mandatory.
- The baseline executor completed one docs-only task end-to-end; the new timer-driven automatic dispatcher has not been exercised end-to-end. Tests use fake CLI/GitHub commands for the broader integrations.
- This implementation is not a hardened multi-tenant service: there is no remote authentication layer, durable process-liveness lease, automated cost accounting, required CI check, or deployment authority. Runner/configured path components are checked for symlinks and other-user write access, but validation is not held through use with open directory handles; same-UID concurrent tampering remains outside this single-user service's security boundary. The PID plus `/proc` start-time check is a conservative recovery guard, not authorization; legacy claims without start-time identity fail closed. The timer's worker/verifier limits are shorter than the recovery window, and its systemd cgroup supervises descendants; direct CLI invocations do not receive that cgroup guarantee.
